# Reusable Gateless Gate case-production contract

## 1. Purpose

This contract converts the proven Case 19 workflow into the manufacturing law
for the remaining Gateless Gate cases. It governs production order, evidence,
authority, validation, review, custody, and failure behavior.

It does not standardize the creative result. Every case must derive its object,
copy, pressure, and composition from its own frozen sources and approved
specification.

## 2. Non-negotiable production law

1. **The page is authored. The artifact is generated.**
2. Generated material is restricted to bounded, registered artifact imagery.
3. Source text, commentary, editorial interpretation, transcription treatment,
   live typography, diagrams, provenance, folios, and page geometry remain
   authored, editable, and separately traceable.
4. The compiler is a deterministic assembler and validator. It may not redesign
   objects, revise copy, force a repeated template, bake text into imagery, or
   infer missing authority.
5. Every state transition is explicit, machine-readable, and fail-closed.
6. No completed page may conceal a missing source, object, artifact view,
   approval, component, or QC receipt.

## 3. Canonical issue anatomy

Every issue contains four authored pages in this order:

1. Artifact
2. Liturgical Hymn
3. Gradient Translation
4. Archive Commentary

The order and functions are fixed. Layouts are not. Repeated page skeletons are
prohibited when they ignore the artifact's actual silhouette, scale, density,
orientation, material behavior, or negative space.

The page system is matte black with restrained argent/silver/white live
typography. White, cream, or gray-paper page fields and black-on-white review
surrogates are prohibited. Review materials must preserve the actual polarity.

## 4. Required case inputs

Before production, each case must have:

- one canonical case identity and destination;
- frozen source-text boundaries;
- separately identified Mumon and Yamada commentary boundaries;
- registered editorial interpretation and object pressure;
- prohibited-imagery rules;
- a case-specific artifact specification;
- a transcription witness registered by checksum, or an explicit
  `WITNESS_ABSENT` state;
- case-specific visual and semantic QC criteria;
- explicit authority for the next bounded stage.

Missing or unverified inputs remain named holds. They are never filled with
plausible text, placeholder imagery, or inferred approval.

## 5. Mandatory isolated forensic-artifact stage

Every physical object required by the issue must be registered before page
design and rendered independently of typography, layout, and page furniture.

Each registered object requires:

- a clean, high-resolution black-and-white forensic master;
- a full-object evidence view;
- an alternate, orthographic, or construction view;
- a macro/detail view of the meaningful intervention, damage, residue, wear,
  seam, or material event;
- material texture, scale, construction, and physical credibility sufficient
  for evidentiary reading;
- filenames, versions, dimensions, checksums, derivation, and approval state;
- a contact sheet showing the views together without page design;
- an explicit founder disposition before any view enters assembly.

If an alternate or macro function truly does not apply, the object register must
name the view `NOT_APPLICABLE`, state why, and receive founder approval for that
exception. Silence is a failure.

An icon, vector trace, diagram, geometry wireframe, illustration, layout crop,
contact-sheet crop, or embedded page image can never satisfy the artifact stage.
Such material may survive only as a registered secondary layer.

## 6. Component stage

After the isolated artifact set is founder-approved, the lane may create only
the separately authorized components:

- final editable four-page copy;
- transcription derivative, when separately authorized;
- live SVG/vector typography for all page text;
- case-specific layout specification;
- page-level source and provenance records;
- component review renders in the true black/argent polarity.

Artifact masters, source witnesses, derivatives, copy, typography, layout,
review renders, and assembled pages must retain separate identities.

## 7. Assembly stage

Assembly is allowed only when the compiler can prove:

- all inputs are registered and checksum-valid;
- all required artifact views are founder-approved;
- every page has editable live typography;
- imagery and typography remain separable;
- the matte-black/argent system is preserved;
- layout responds to the case's actual artifact;
- no forbidden downstream authority is open.

The compiler may place and crop approved components responsively. It may not
generate, rewrite, restyle, repair, or replace them.

## 8. Rendered visual QC

Structural validation is necessary and insufficient. The actual combined review
PDF and its page renders must be inspected.

QC must reject:

- white-paper polarity or black typography;
- clip art, badge, icon, vector, or generic illustration substituted for the
  forensic object;
- missing object views;
- text collisions, clipping, overflow, unsafe cropping, or illegibility;
- image-baked authoritative text;
- a mechanically repeated layout skeleton;
- broken PDF joins, missing headers, damaged folios, or resource loss;
- dense explanatory copy that turns the issue into a design specification;
- mismatch between the approved artifact and the assembled page;
- any source, checksum, or authority inconsistency.

A structural `PASS` cannot overrule a visual `FAIL`.

## 9. Founder review gates

There are two mandatory creative gates per case:

1. `FOUNDER_REVIEW_ISOLATED_ARTIFACT_SET`
2. `FOUNDER_REVIEW_ASSEMBLED_CASE_PROOF`

Multiple cases may be presented in one bounded review wave to reduce founder
clicking. Each object and each assembled issue must still receive an explicit
`APPROVE`, `PATCH`, or `REJECT` disposition. Approval of one case never grants
authority to another.

## 10. Persistent custody

A stage is incomplete until its files are:

- saved in the canonical case hierarchy;
- named and versioned;
- checksum-covered;
- registered with source-to-derivative links;
- accompanied by authority, validation, QC, and approval receipts;
- reflected in the project control record.

Recommended relative case hierarchy:

`CASES/CASE_##/{00_SOURCE,01_SPECIFICATION,02_ARTIFACT,03_TRANSCRIPTION,04_COPY,05_SVG_TEXT,06_LAYOUT,07_PROOFS,08_EXPORTS,09_CONTROL}`

## 11. Fail-closed blockers

The case must return `NOT_ELIGIBLE` when any of the following is true:

- source identity, destination, version, or checksum is missing;
- witness state is neither verified nor explicitly absent;
- object register is missing;
- full, alternate/construction, or macro/detail view is missing without an
  approved `NOT_APPLICABLE` exception;
- any required artifact view is not founder-approved;
- typography or page design is baked into an artifact master;
- a vector, diagram, or page crop is presented as the primary artifact;
- copy, typography, layout, or provenance is missing or unapproved;
- page assembly begins before artifact approval;
- rendered visual QC is missing or failed;
- an assembled proof differs from its registered inputs;
- production attempts to advance beyond its explicit authorization.

## 12. Scaling boundary

Contract approval would make the method reusable; it would not authorize
production. Remaining cases require a separately bounded authorization naming
the cases, the permitted stages, and the founder return gate.

Publication, release, archive admission, and canon admission remain separate
human-authority decisions after production.
